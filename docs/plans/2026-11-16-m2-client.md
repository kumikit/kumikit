# M2 — Client

- **Goal:** reach the exit criteria of [M2](../spec/12-roadmap.md#m2--client): from the
  desktop app a user installs an ACP provider, starts a thread, approves a tool call and
  switches themes; closing and reopening the window resumes the running turn. Nothing from
  M3 (remote cores, WebSocket/TLS, pairing, device tokens, SSH, multi-core UI) or M4
  (registry, signing, updates, lockfiles, level-2 iframe panels, `kumikit theme check`).
- **Status:** active (approved 2026-11-16).

## Scope

In:
- `crates/kumikit-shell` (Tauri 2): window, the UI served from a custom protocol, local
  core discovery and detached start, the connection bridge, UI plugin files from
  `kumikit-plugin://<id>/` with a strict CSP, the client plugin store (Q2).
- `crates/kumikit-package`: the defensive `.kkp` pack/unpack code, moved out of
  `kumikit-plugin-host` so the shell can use it without the kernel (Choice B).
- `web/kernel` (Svelte 5): connection manager (one local connection, state shaped per
  connection), tabs, thread store, slot registry, command registry and palette, theme
  engine, declarative renderer, plugin manager.
- `web/sdk` (`@kumikit/ui-sdk` 0.1): level 1 (declarative) and level 3 (inline modules).
- `plugins/ui-chat`, `plugins/ui-settings`, `plugins/theme-default`, and their bundling.
- The core: the protocol additions below, `kumikit serve --bundled-plugins <dir>`
  (preinstall), `plugin.install` from a directory.
- Tests: Vitest, svelte-check, Playwright against the browser build, Rust tests for the
  shell, the desktop exit test over WebDriver, one ignored live test.
- Footprint checks for the shell, the UI kernel bundle and the installers; CI jobs.

Out (deferred, with the reason):
- `settings.*` methods and the `kumikit:host/settings` interface: no M2 core plugin has
  settings (`contributes.settings` is false for all of them), and the exit criteria do not
  need them. The declarative settings form is still built and tested: ui-settings renders
  the client's own settings with it, and fixtures cover plugin schemas. They land with the
  first core plugin that has settings.
- `secret.*` methods and the OS keychain: no M2 plugin requests a secret (Claude Code
  uses its own login). They come with `settings.*`.
- `command.*`, `kumikit:plugin` `run-command`/`handle-rpc`, `<pluginId>/*` methods: no
  core plugin contributes commands yet. The palette has kernel and UI plugin commands.
- The `core` topic (plugin failures) and the `approvals` topic: failures already show on
  the failed turn (`turn.ended` `error`) and in `plugin.list` (`failure`), and a
  pending approval shows through the thread's status on the `workspace:<id>` topic (below).
  They get delivery rules when a UI needs more.
- The "starter pack" first-run screen (10-distribution): it offers plugins from the
  registry (M4). M2 installs from files and folders.
- Level-2 iframe panels (M4): a UI manifest with `isolation = "iframe"` is refused at
  install with "needs a later Kumikit".
- Browser client served by a core (M3 transport). The browser *build* exists for tests
  (see Tests).

## Design

### Crates, packages and dependency rules

```
kumikit-protocol ← kumikit-kernel ← kumikit-plugin-host ← kumikit-core
kumikit-package  ← kumikit-plugin-host, kumikit-shell, kumikit-core (pack)
kumikit-protocol ← kumikit-shell
@kumikit/protocol ← web/kernel, web/sdk
@kumikit/ui-sdk   ← web/kernel, plugins/ui-*
```

- `kumikit-package` has no workspace dependencies and no kernel types: `pack`, `unpack`,
  `sha256_file`, the size and entry caps. `kumikit-plugin-host` re-exports nothing new;
  it just calls it. 01-architecture gains the crate and the rule.
- `kumikit-shell` uses `kumikit-protocol` only for the local address. The per-platform
  socket and pipe rules in `kumikit-core/src/paths.rs::default_address` are protocol
  rules (02-protocol), pure and I/O-free, so they move to `kumikit_protocol::local` with
  the env lookup injected as today. The core and the shell then compute the same address.
  The client data directory (01-architecture) is computed in the shell.
- No workspace crate depends on `kumikit-shell`.

### Shell (`crates/kumikit-shell`)

The crate is a library (discovery, core start, bridge, plugin store, asset responses,
CSP), which holds all the logic and is tested without a window, plus a thin `main.rs`
that wires it into Tauri.

- **Window and UI.** One window. The UI kernel's built files are app resources served
  from the custom protocol `kumikit-app://localhost/` (not Tauri's compile-time asset
  embedding), so `cargo build -p kumikit-shell` does not need Node or a built `web/`
  (Choice C). The same responder serves plugins. Dev mode uses Vite's dev server
  (`devUrl`). The webview's data directory is inside the client data directory
  (01-architecture).
- **CSP** on every response: `default-src 'none'; script-src 'self' kumikit-plugin:;
  style-src 'self' kumikit-plugin:; img-src 'self' kumikit-plugin: data:; font-src 'self'
  kumikit-plugin:; connect-src ipc: http://ipc.localhost; base-uri 'none'; form-action
  'none'; frame-src 'none'`. No `unsafe-inline` or `unsafe-eval`. The theme engine sets
  tokens through the CSSOM (a constructed stylesheet), which the CSP does not block. On
  Windows, WebView2 exposes custom schemes as `http://<scheme>.localhost/`; the CSP lists
  the form the platform uses (Q3).
- **Local core.** `connect("local")`: connect to the local address. If nothing answers,
  start the bundled `kumikit serve --bundled-plugins <resources>/core-plugins` detached
  and wait for its `ready <address>` line (no polling). The shell does not stop the core
  when it exits. Unix: a new process group (`process_group(0)`), stdin and stderr null,
  stdout piped only until `ready`. Windows: `CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW
  | CREATE_BREAKAWAY_FROM_JOB` (falling back without breakaway if the job forbids it).
  If two windows race, the loser's `serve` fails on the lock and it connects to the
  winner's core. The core binary is found next to the shell executable (Tauri
  `externalBin`), never on `PATH`. Test and dev overrides use environment variables
  (`KUMIKIT_SOCKET`, `KUMIKIT_CORE_DATA_DIR`, `KUMIKIT_CLIENT_DATA_DIR`,
  `KUMIKIT_CORE_BIN`), each documented in 06-client.
- **Bridge.** Tauri commands `bridge_connect(profile, channel) → connectionId`,
  `bridge_send(connectionId, line)`, `bridge_close(connectionId)`. Incoming lines go to
  the UI over the `tauri::ipc::Channel` given at connect, in order. The shell does not
  parse JSON-RPC. It enforces the 8 MiB line limit and reports `closed { reason }` when
  the socket closes. Profiles are names, not addresses: M2 accepts only `local`, so the
  webview cannot open arbitrary sockets. Connections are keyed by id, so M3 adds remote
  profiles without changing the API (Choice D).
- **Client plugin store** (Q2): `client_plugins_list`, `client_plugins_install(path)`,
  `client_plugins_remove(id)`. The store unpacks `.kkp` files with `kumikit-package`
  into `<client data>/ui-plugins/<id>/<version>/`, checks the UI and theme manifest's
  structure (below), and lists bundled plugins from the app resources (read-only) next to
  installed ones. Enabled state and trust are client settings in the UI kernel (below).
- **Native file picker:** `tauri-plugin-dialog`, with only the `dialog:allow-open`
  capability granted. No other Tauri plugins: no shell, fs, http, updater or tray.
- Capabilities: the window may call the bridge, the plugin store and `dialog:allow-open`.
  Nothing else.
- **Test hooks** behind a cargo feature `test-hooks`, which release builds never enable:
  `KUMIKIT_TEST_PICK=<path>` makes the file picker return that path (WebDriver cannot
  drive native dialogs), and the shell prints `ui-connected` on stdout after the first
  bridge connection succeeds (used by the footprint check).

### UI kernel (`web/kernel`)

Svelte 5 runes, TypeScript strict, Vite. State lives in plain TypeScript classes in
`.svelte.ts` files with `$state` fields. Logic that does not need Svelte (event folding,
fuzzy matching, token validation, permission wording) is plain functions, tested in
Vitest without a DOM (Choice A).

- **Platform adapter** (`platform/`): `connect(profile, onLine) → Connection`,
  `pickFile(filters)`, `pickFolder()`, `pluginUrl(id, path)`, `clientPlugins`. The
  implementations are `tauri` (the shell bridge) and `relay`, which is test-only, built
  into the browser test bundle and never into the desktop bundle (see Tests). M3 adds a
  WebSocket implementation.
- **Connection manager:** per connection, it holds the status (`connecting`, `ready`,
  `reconnecting`, `failed`), the `core.hello` result, plugins (updated by
  `core.pluginsChanged`), workspaces, providers, subscriptions and the last `seq` per
  thread. It reconnects with backoff (0.5 s doubling to 30 s). On reconnect it redoes
  `core.hello` and resubscribes every topic with its last `seq`. A JSON-RPC client keeps
  request ids per connection and reports `data.code` as typed errors. A
  `protocol_mismatch` shows "This window and the running core are different versions"
  with a restart action (Q8).
- **Tabs:** each tab is `(connection, workspace)`. Open tabs are kept in client settings.
  Addresses are `<connection>/<workspace>/<thread>`.
- **Thread store:** one wire subscription per topic per connection, because the protocol
  allows only one (02-protocol). The store subscribes `thread:<id>` with `after: 0`, keeps
  the events in memory, and folds them into a view (turns, messages, tool calls, pending
  approvals, status, usage). Subscribers, the kernel and plugins alike, get the folded
  view and the event list. `text.delta` folding is batched per animation frame; input
  never waits on it. On reconnect it resubscribes with the last `seq`; a duplicate or
  gap check fails loudly in tests. The fold's status must agree with the core's
  `fold::next_status`; a shared fixture (recorded event logs with the expected statuses)
  is checked by both a Rust test and a Vitest test.
- **Sidebar:** workspaces and their threads (`thread.list`, kept current by the
  `workspace:<id>` topic), with the status of each thread (running, awaiting approval).
  Plugins add `sidebar.section`s.
- **New thread:** a provider and model picker from `provider.list` and
  `provider.models`. Workspaces are opened with the folder picker (`workspace.open`).
- **Slot registry:** the slots in 07 plus `thread.view` (Q5). Each contribution is
  mounted into its own element, inside an error boundary. A `mount` that throws shows an
  error placeholder; after 3 failures in a session the plugin is disabled and the user is
  told.
- **Command registry and palette:** kernel commands (new thread, switch theme, open
  plugin manager, …), UI plugin commands, and, when they exist, core plugin commands.
  Fuzzy match, `when` clauses limited to a small context (`thread.open`,
  `connection.ready`), and keybindings. Every kernel action has a command.
- **Theme engine:** reads a theme's variant tokens, validates each value by type (color,
  length, font list, duration, shadow, number), and rejects invalid ones with a message.
  It maps `a.b` to `--kk-a-b` and writes the tokens to one constructed stylesheet. Missing
  tokens come from the fallback theme's variant of the same appearance. Platform modes are
  media queries the engine writes after the theme, so a theme cannot override them:
  `prefers-contrast: more` (solid borders, no shadows), `prefers-reduced-transparency`
  (opaque overlays), `forced-colors: active` (system colors), `prefers-reduced-motion`
  (zero durations). Base CSS uses `var(--kk-…, <system color>)` (Canvas, CanvasText,
  …), so the UI stays usable with no theme at all ("works with an empty state",
  10-distribution). The appearance follows the system by default.
- **Declarative renderer:** settings forms (a JSON Schema subset: string, number,
  boolean, enum, object one level deep; `x-widget`, `x-secret`, `x-order`), commands,
  status items, the views `list`, `tree`, `table`, `markdown`, `key-value`, `form`,
  `progress`, notifications and quick picks. Each has Vitest fixtures. In M2 the data
  comes from UI plugin manifests and ui-settings; core plugins provide none yet.
- **Markdown:** one renderer in the kernel, used by the `markdown` view and exposed to
  plugins as `ctx.ui.markdown(el, text)`, so ui-chat does not bundle its own. Raw HTML is
  escaped, never rendered. Links are limited to `http`, `https` and `mailto` and open
  outside the app only after a confirm (Q11). Choice F.
- **Plugin manager** (part of the kernel):
  - Core plugins (`plugin.*`): list, install from a `.kkp` (file picker) or a folder with
    a `plugin.toml` (folder picker), permissions shown in plain words with the same
    wording as the CLI, an "unsigned" warning, and grant as a whole, plus enable, disable
    and uninstall with "delete data?". `spawn` gets the prominent warning from
    04-plugin-host.
  - Client plugins: list (bundled and installed), install from a `.kkp`, enable,
    disable, remove. Installing a third-party inline UI plugin asks for trust: "runs with
    full access to this app and every connected core". Themes need no trust.
  - **Safe mode:** starting with `?safe` (or Shift held at launch, read by the shell and
    passed as a query parameter) loads no UI plugins, so a broken plugin can always be
    removed.
- **Client settings** (theme, appearance, open tabs, enabled and trusted UI plugins,
  per-plugin `ctx.storage`) live in the webview's `localStorage`, which sits in the client
  data directory. Nothing secret is stored there.
- **Fallback theme and bundled plugins** come from a data file in the app resources,
  `bundled.json`: `{ uiPlugins: [...], fallbackTheme: "<id>" }`. Kernel code names no
  plugin; `check-plugin-names.sh` extends to `web/kernel/src`, `web/sdk/src` and
  `crates/kumikit-shell/src`.

### UI SDK (`web/sdk`, `@kumikit/ui-sdk`)

- Version **0.1.0**, versioned like the WIT packages: 0.x until third parties publish
  (M4), frozen at 1.0. Manifests of UI plugins and themes say `api = "^0.1"` (Q4).
- Framework-agnostic types only (no Svelte types): `Plugin { activate(ctx), deactivate? }`,
  `ctx.slots.register`, `ctx.commands.register/run`, `ctx.connection` (`call`,
  `subscribe`, limited to the methods the manifest declares: `requires.core` methods plus
  read-only kernel methods, enforced by the kernel's proxy), `ctx.threads.watch(address,
  fn) → unsubscribe` (the kernel's folded thread view; added, Q6), `ctx.theme.tokens`,
  `ctx.theme.onChange`, `ctx.storage`, `ctx.notify`, `ctx.ui.markdown`.
  `mount(el, props) → unmount`.
- **Public lists:** the slot list (`web/sdk/api/0.1.0/slots.json`) and the token set
  (`web/sdk/api/0.1.0/tokens.json`: each token's name, group and type). The TypeScript
  `Slot` and `TokenName` unions are generated from them. `web/sdk/api/PUBLISHED`
  records a SHA-256 of each published directory, and a Vitest test fails if one changes,
  as `wit/PUBLISHED` does for WIT. A change means a new version directory. The spec's
  `tokens@1` becomes "the token set of UI SDK 0.1" until 1.0 (Q4).
- Level 1 contributions are manifest data, validated against
  `sdk/schema/ui-plugin-manifest.schema.json`.

### UI plugin and theme manifests

Same file (`plugin.toml`), id, name, version, description, license and repository rules
as core plugins. They differ in these ways:

| | Core plugin | UI plugin | Theme |
|---|---|---|---|
| `kind` | provider, tool, bot, integration | `["ui"]` | `["theme"]` |
| `api` | kernel plugin API (`^0.1`) | UI SDK (`^0.1`) | UI SDK (`^0.1`) |
| Code | `[runtime]` WASM | `[ui] entry`, `isolation = "inline"` (`iframe` refused until M4) | none |
| Permissions | `[permissions]` | none; `[requires] core = [...]`, plus trust for inline third-party plugins | none |
| Contributes | providers, commands, settings, … | `slots`, `commands`, `settings` (declarative) | `[theme] variants`, `fonts` |
| Installed by | the core (`plugin.install`) | the shell's client plugin store | the shell's client plugin store |

A package's `kind` is either all core kinds or exactly one of `ui` and `theme`; the two
installers refuse each other's packages with a clear message. The shell checks structure
and that the files exist. The UI kernel checks the contents when it loads them (tokens by
type, slot names, and font files that are `woff2`). JSON Schemas live in `sdk/schema/`.
`requires.core` is parsed and stored; gating on it comes in M3 (on the single local core
it is checked against `core.hello` plugins at activation).

### First-party plugins

- **ui-chat** (Svelte, inline): `thread.view` (the transcript and the composer),
  `transcript.renderer` for every kernel event kind (text with markdown, reasoning folded,
  tool calls with output and result, `file.changed` with the diff, approvals with Allow,
  Allow always and Deny, usage, turn end and errors), a generic `plugin.event` fallback
  (kind and JSON, collapsed), `thread.header` (status, cancel). Enter sends and
  Shift+Enter adds a newline; Escape cancels the turn after a confirm. Both are IME-safe.
  Messages sent during a turn show as queued.
- **ui-settings** (Svelte, inline): `settings.page`s for appearance (theme, variant or
  "follow system", reduced motion override) and plugins (each plugin's declarative
  settings, when any), rendered with the declarative form.
- **theme-default** (data): `light` and `dark` variants that define every token in the
  token set and pass WCAG AA (a Vitest contrast test, until `kumikit theme check` in M4).
- **Build:** each UI plugin is an npm workspace package built with Vite library mode into
  one ES module (`dist/index.js` plus CSS). Svelte plugins bundle their own Svelte
  runtime, because Svelte is not part of the SDK (ADR 0004). `npm run build` writes
  `<plugin>/dist`. A script packs each plugin with `kumikit plugin pack`'s format
  (`kumikit-package`) into `target/bundle/ui-plugins/*.kkp`.
- **Bundling:** the app resources carry the kernel bundle, the bundled UI plugins
  (unpacked, read-only), `bundled.json`, and `core-plugins/kumikit.provider-acp-<v>.kkp`.
- **Preinstalling provider-acp on the core:** `kumikit serve --bundled-plugins <dir>`.
  On start the core installs each `.kkp` in the directory that it has never seeded
  before. It records each seeded id and version in the kernel's records, so a plugin the
  user removed is not reinstalled. It enables only plugins that request no permissions;
  others stay installed and wait for a grant. provider-acp requests none. The core names no
  plugin. If the core was already running without the flag (started from the CLI), nothing
  is preinstalled until it next starts from the app; the plugin manager shows it as
  missing (10-distribution updated, Q7).

### Installing an ACP provider from the desktop

`plugin.install { path }` reads a path on the core's machine, which in M2 is always this
machine:
- A `.kkp`: the file picker returns its path.
- A declarative provider folder such as `plugins/provider-acp/examples/claude-code`: the
  folder picker returns the directory and `plugin.install` accepts a directory that holds a
  `plugin.toml`. The core packs it in memory with the same code as `kumikit plugin pack` and
  installs the result, so the recorded SHA-256 is that of the packed archive.
Then the permission dialog, `plugin.enable { grant }`, and `core.pluginsChanged` updates
the provider list.

## Protocol changes

All additive, so all **minor** per AGENTS.md. During 0.x both sides need the same minor,
so the version goes `0.2` → `0.3`. The desktop app bundles its core, so they match.
TypeScript is regenerated and fixtures are added for every new method, notification and
event.

| Change | Class |
|---|---|
| `provider.list` → `{ providers: [{ id (qualified), name, plugin }] }`, from manifests, no activation | minor (new method) |
| `provider.models { provider }` → `{ models: [{ id, label, capabilities }] }`, activates the provider's plugin (`list-models`) | minor (new method) |
| `workspace:<id>` topic defined: events `thread.created { thread }`, `thread.updated { thread }` (status, title, `updated`), `thread.archived { thread }`. No replay: `after` must be 0, `head` is 0, only live changes follow. A client subscribes first, then calls `thread.list`, and keeps the copy with the later `updated` | minor (defines a reserved topic; new event kinds on a new topic) |
| `plugin.install { path }` accepts a directory holding a `plugin.toml` | minor (wider accepted input) |
| `capabilities` gains `providers` and `workspace_events` | minor (new strings) |
| `core.shutdown` → `{}` (Q8, accepted): ends running turns as on a normal stop; the app asks before calling it | minor (new method, reserved in 02) |

Not changed: `thread.*`, `events.subscribe` on threads, `plugin.list/enable/disable/
uninstall`. The permission wording stays in the clients (CLI and UI) and a shared fixture
keeps them the same.

## Tests

- **Rust (shell, all three OSs):** address computation (moved tests), discovery when a
  core answers; when nothing answers, starting a real `kumikit serve` detached and
  checking it keeps answering after the shell's handle is dropped; a race of two starters;
  bridge round trip with a real core (hello, subscribe, line limit, close reported); the
  asset responder (MIME types, CSP header on every response, no path traversal outside
  the plugin directory, unknown plugin is 404); the client plugin store (install, refuse a
  core package, refuse `iframe`, remove). The core gets tests for `--bundled-plugins`
  (seeded once, not reinstalled after removal, permissioned plugins not enabled), the
  directory `plugin.install`, `provider.*` and the `workspace:<id>` topic.
- **Vitest + svelte-check (`web/`):** fold (including the shared status fixture), the
  JSON-RPC client and reconnect logic against an in-memory fake connection, theme value
  validation (including injection attempts such as `red; background: url(…)`), contrast of
  theme-default, the slot error boundary and disable-after-3, the palette matcher,
  declarative renderer fixtures, permission wording against the shared fixture,
  `PUBLISHED` hashes. Components are tested with jsdom and Svelte's `mount`.
- **Playwright against the browser build** (Chromium and WebKit, Choice G): the browser
  client in 06 needs a core serving the UI, which is M3. Instead, tests use
  `test-plugins/web-relay`, a test-only Rust binary that serves the built browser bundle
  on `127.0.0.1:<random port>` and relays one WebSocket to a real `kumikit serve` on a
  temp socket, speaking the same line protocol as the shell's bridge. The page uses the
  `relay` platform adapter. The core runs `fake-acp-agent replay <transcript>` on its
  `PATH`, as `exit_m1` does, so turns are real and deterministic. The relay can drop the
  WebSocket on request, which tests reconnect: no gap, no duplicate, and the
  "reconnecting" state shown. The file and folder pickers return paths set by the test.
  No sleeps: tests wait on DOM state and on the relay's `ready` line. Loopback only; the
  relay is never shipped. The suite covers the exit flow plus a theme from a `.kkp`, safe
  mode, a throwing plugin, keyboard-only paths, and axe-core accessibility checks.
- **Desktop exit test** (`web/e2e-desktop`, WebdriverIO + `tauri-driver`, Choice H): the
  real app built with `test-hooks`, isolated socket and data directories, and the fake
  agent on the core's `PATH`. Steps:
  1. Start the app. It starts the core with `--bundled-plugins`, and provider-acp shows
     as enabled.
  2. Install the Claude Code example folder (the picker hook), check the permission text,
     grant.
  3. Open a workspace, create a thread with `community.claude-code/claude`, and send
     the message from `claude-tool-allow`. The approval card appears.
  4. **Close the window:** the app exits and the core keeps running (checked through its
     socket).
  5. **Reopen:** start the app again. It finds the running core, the thread shows the
     same pending approval, and the status is "awaiting approval".
  6. Allow. The turn ends `done` with the `file.changed` diff shown.
  7. Switch to the dark variant from the palette and check that `--kk-surface-panel`
     changes, then switch back.
  Per platform:
  - **Linux:** xvfb, with `WebKitWebDriver` from `webkit2gtk-driver` in CI.
  - **Windows:** `msedgedriver` matching the runner's WebView2 version.
  - **macOS:** WKWebView has no WebDriver. The same flow runs there through Playwright
    WebKit against the browser build, and the "close and reopen" part is covered by the
    shell's Rust tests (a detached core survives the shell; a new shell reconnects). The
    plan reports macOS as not driven end to end.
- **Live test** (ignored, Linux, manual): the same desktop flow with real
  `claude-agent-acp` on `PATH` and a prompt that edits a file.

## Footprint

| Budget | How it is measured | Where |
|---|---|---|
| Shell ≤ 25 MB resident, excluding the webview | Release build with `test-hooks`, under xvfb. Start, wait for `ui-connected`, wait 1 s, read the shell process's own RSS (`/proc/<pid>/status`; WebKitGTK's web and network processes are children and are not counted). Median of 5 | `scripts/footprint.sh`, CI on Linux. Also reported, not gated: macOS (`ps -o rss`), Windows (`Get-Process`) |
| UI kernel ≤ 150 KB compressed JS | Sum of gzip -9 sizes of the kernel's JS chunks in `web/kernel/dist` (plugins and the protocol types excluded; plugins reported separately) | `web/scripts/size.mjs`, run by `npm test` and CI |
| Installer ≤ 20 MB per platform | Size of the `.deb` and `.rpm` (Linux), `.dmg` (macOS) and NSIS `.exe` (Windows) built by `tauri build` in CI. The AppImage bundles WebKitGTK and is not a target (Q9). WebView2: `embedBootstrapper` or `skip` (no download at install) | A CI `installers` job on 3 OSs, which checks sizes and uploads the installers as artifacts (not released) |

Release profile: **no change now.** The core is 25.3 MiB raw and 6.8–9.6 MiB
compressed, and the shell should add 3–6 MiB compressed, so the installers should fit
with room. If one does not, the first lever is per-package overrides
(`[profile.release.package.cranelift-codegen] opt-level = "s"` and the same for the
wasmtime crates), which keep the kernel at `opt-level = 3`. Global `opt-level = "s"`
(19.1 MiB) is second. Both are measured against the activation budget first.

Risk: the WebKitGTK UI process (GTK plus WebKit's UI side) may be over 25 MB by itself.
Step 2 measures a bare window first. If it is over, I stop and ask; I do not change the
budget.

## UI rules (how they are checked)

- Tokens only: a small script, `web/scripts/check-tokens.mjs` (no Stylelint), fails on color
  literals (`#…`, `rgb(`, `hsl(`, named colors), `px`/`rem` in `border-radius`,
  `font-size` or `box-shadow`, in `web/kernel/src` styles. System color keywords in
  fallbacks are allowed.
- Input is never gated: no `disabled` tied to pending network calls in the composer (a
  send during a turn is queued by the core). Animations have `prefers-reduced-motion`
  paths and the zeroed motion tokens.
- Keyboard: every action is in the palette, focus is visible (`:focus-visible` ring
  from `--kk-focus`), focus is trapped in dialogs and restored. Playwright runs a
  keyboard-only pass of the exit flow.
- IME: a shared `isComposing(event)` helper (checks `isComposing` and keyCode 229) is
  used by every Enter or Escape handler. A Vitest test covers it, and a lint script
  fails on `key === 'Enter'` without it.
- Accessibility: semantic elements, ARIA only where needed, live region for streaming
  text (polite, coalesced), axe-core in Playwright, forced-colors respected.

## Questions (unclear or possibly wrong in the spec)

Answered 2026-11-16: Q1 yes (the shell may start its bundled core; ADR 0013 records it),
Q2 yes (client plugin store in the shell), Q4 yes (UI SDK 0.1, `api = "^0.1"`), Q8 yes
(add `core.shutdown`), Q12 yes (install `tauri-driver` and a WebKitGTK WebDriver). No
package on this machine's repositories or the AUR ships `WebKitWebDriver`, so see the
follow-up in Notes. Q3, Q5–Q7, Q9–Q11 and Q13 are still open.

1. **Starting the core outside the supervisor.** AGENTS.md says "External programs run
   only through the kernel's process supervisor", but the shell cannot use the kernel and
   must start `kumikit serve`. I recommend reading the rule as applying to the core, with
   ADR 0013 recording the one exception: the shell starts only its own bundled core
   binary, by absolute path.
2. **The shell installs UI plugins.** 06 says the shell has no feature commands, and 10
   says UI plugins and themes are installed "locally". Only native code can write the
   client data directory. I recommend a narrow client plugin store (install, list,
   remove) in the shell, listed in 06 next to "UI plugin files".
3. **`kumikit-plugin://<id>/` on Windows.** WebView2 serves custom schemes as
   `http://kumikit-plugin.localhost/<id>/`. I recommend that the spec name the scheme, the
   platform adapter build the URLs, and the CSP list the platform's form.
4. **UI API version.** The 07 and 08 examples say `api = "^1.0"` and `tokens@1`, but
   nothing is frozen and third parties cannot publish until M4. I recommend UI SDK 0.1.0
   with `api = "^0.1"`, frozen at 1.0, and the same `PUBLISHED` protection as WIT. This
   is the same reasoning as M1's Q2.
5. **Where a thread is shown.** No slot holds the main thread view, and the kernel cannot
   name ui-chat. I recommend a new slot, `thread.view`: the kernel mounts the first
   enabled contribution (a minor SDK addition).
6. **One subscription per topic.** The protocol allows one subscription per topic per
   connection, so plugins cannot subscribe to a thread themselves next to the kernel. I
   recommend that the kernel own all wire subscriptions and that plugins read the kernel's
   folded view through a new `ctx.threads.watch`. `ctx.connection.subscribe` then fans out
   from the kernel's subscription.
7. **Preinstalling provider-acp.** I recommend the core-side `--bundled-plugins <dir>`
   (seed once, enable only permission-free plugins) over the UI installing it on first
   connect, because it works the same for every client and leaves no race between
   windows.
8. **A running core of another version.** After an app update, an old core may still run,
   and `core.hello` fails with `protocol_mismatch`. Options: (a) add `core.shutdown`
   (reserved in 02) and offer "Restart the core (running turns end)"; (b) only show the
   error with how to stop it. I recommend (a).
9. **Installer budget on Linux.** An AppImage bundles WebKitGTK and cannot meet 20 MB. I
   recommend the budget cover `.deb`, `.rpm`, `.dmg` and NSIS `.exe`, and that 00 say so.
   Installers are unsigned CI artifacts in M2. Code signing and notarization come with
   releases.
10. **Does "switches themes" include another theme?** theme-default's light and dark are
    enough for the exit test, as I read it. The browser suite also installs a test theme
    from a `.kkp`.
11. **Links in agent output.** Opening a URL in the system browser needs a shell
    capability (`opener`), which is a native command and outgoing traffic the user
    starts. I recommend copy-to-clipboard only in M2 (no opener plugin), and deciding
    opening in M3. Otherwise I add `tauri-plugin-opener` limited to `http(s)` behind a
    confirm.
12. **Installs on this machine.** The desktop e2e needs `tauri-driver` (`cargo install
    tauri-driver --locked`) and `WebKitWebDriver`, which Arch's `webkit2gtk-4.1` does not
    ship. Playwright's browsers are already cached. May I install `tauri-driver` and a
    WebKitGTK WebDriver (for example the AUR `webkit2gtk-4.1` build with the driver, or
    the Flatpak SDK)? If not, the desktop e2e runs only in CI and I say so.
13. **Webview telemetry.** Tauri sends nothing, but WebView2 on Windows follows Windows'
    diagnostic settings. I recommend a sentence in the README's privacy section and
    nothing more.
