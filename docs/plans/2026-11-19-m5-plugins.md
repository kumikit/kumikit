# M5 — Plugins

- **Goal:** build the plugins of [M5](../spec/12-roadmap.md#m5--plugins): adapters for
  popular agent CLIs, the tool gateway (MCP), git and GitHub, a Telegram bot and schedules
  (the VS Code theme importer is dropped, below). Each one is a separate plugin, built only with the public
  SDKs. Where a plugin needs something the kernel lacks, a general API lands first, in its
  own step, with spec, tests and (for published interfaces) an ADR. Nothing after M5: no
  interface freeze, no 1.0 release work, no mobile client.
- **Status:** active (approved 2026-11-19 with the answers under Questions).

## Scope

In:
- **General APIs** (in this order): secrets and plugin settings over the protocol; WIT
  0.2.0 (plugin methods, commands, settings, timers, a client interface, typed MCP
  endpoint) and the SDK crates; plugin methods and core commands; outgoing HTTP for
  plugins; the client interface with linked workspaces; schedules; the tool gateway.
- **Plugins:** declarative ACP providers for GitHub Copilot CLI, OpenCode, Gemini CLI and
  Cursor CLI; a WASM adapter for Claude Code (its own `stream-json` protocol), which is
  also a provider backend; DeepSeek through that backend as a community example;
  `kumikit.git` with a sandboxed panel `kumikit.ui-git`; `kumikit.github`;
  `kumikit.bot-telegram`; `kumikit.schedules`.
- **Test tools:** fake MCP client steps in `fake-acp-agent`, fake Bot API, fake GitHub
  API; `fake-acp-agent replay` also replays Claude Code's `stream-json`.
- **Publishing** of the first-party plugins to `github.com/kumikit/registry`, with you
  signing (step P).
- **A written freeze review** for ADR 0020 (what M5 taught about WIT and the UI SDK). The
  freeze itself (1.0.0) is not in M5.

Out: the VS Code theme importer (removed from 08-themes and the roadmap), WIT/UI SDK 1.0.0, opening the registry to third parties, `kumikit:host/files`
(no M5 plugin needs it; see the freeze review), inbound webhooks for bots, Slack/Matrix
bots, an API provider with its own agent loop, the mobile client, periodic update checks.

I/O and replays its own transcripts natively.

## Tool gateway

- **Contributing a tool.** A plugin lists its tools in the manifest, so listing them
  activates nothing:

  ```toml
  [[contributes.tools]]
  name = "status"                       # [a-z0-9_]{1,32}
  title = "Git status"
  description = "Changed, staged and untracked files in the workspace."
  input = "tools/status.schema.json"    # JSON Schema of the arguments
  effect = "read"                       # read | write (default write)
  ```

  It implements `kumikit:tool/tool.call(call) -> result<tool-result, error>`, where the
  call carries `name`, `input` (JSON, already validated against the schema by the kernel),
  the thread and the workspace root, and the result is MCP-shaped (`text`, optional
  `structured` JSON, `is-error`).
- **MCP names.** A tool is exposed as `<plugin id with "." and "-" as "_">__<name>`
  (`kumikit_git__status`), at most 64 characters (checked at install).
- **Transport: MCP over stdio, through the core's local socket.** The kernel gives each
  provider session (whose plugin has the `tools` grant) an `mcp-server` record:
  `{ name: "kumikit", command: <absolute path of the core binary>, args: ["mcp",
  "--socket", <socket>], env: [("KUMIKIT_MCP_TOKEN", <token>)] }`. The provider passes it
  to its agent (ACP `mcpServers`; Claude Code `--mcp-config`). The agent starts `kumikit mcp`,
  which connects to the local socket or pipe, sends `gateway.attach { token }` as its
  first message, and from then on copies MCP's newline-delimited JSON-RPC both ways. Why
  stdio: every ACP agent must support stdio MCP servers (HTTP is optional), and the local
  socket already has the 0600/peer-credential (and pipe ACL) checks, so no TCP port is
  opened and no other local user can reach it.
- **Auth.** The token is 32 random bytes, held only in memory, bound to one provider
  session (thread, workspace, provider), passed in the environment (not on a command
  line), and void when the session ends, the plugin is disabled or the core stops.
  `gateway.attach` works only on local connections; remote ones get `permission_denied`.
- **What the server speaks.** MCP `initialize` (protocol versions 2025-03-26, 2025-06-18
  and 2025-11-25), `notifications/initialized`, `ping`, `tools/list`, `tools/call`,
  `notifications/cancelled`. No resources, prompts, sampling or elicitation. Own small
  implementation over the existing message reader (no MCP crate).
- **Which tools a session sees:** every tool of every enabled plugin with kind `tool`
  (later: per-workspace choices). `notifications/tools/list_changed` when plugins change.
- **Calls.** The kernel checks the input against the schema, appends `tool.started`
  (`source { plugin, tool }`), activates the tool plugin's instance for that thread
  (acting for its workspace, so `git` runs there), calls it, and appends `tool.output` /
  `tool.finished`. A call outside a running turn of its thread is refused (the agent got
  the tool from that turn's session).
- **Approvals.** A `write` tool needs an approval in the running turn (kind `tool`,
  summary "Run `kumikit_github__create_pull_request`", detail = the input), appended by the kernel. `allow_always`
  covers that tool in that thread (folded from the log, so it survives restarts). `read`
  tools run without asking. Agents that also ask before MCP calls (Claude Code in
  `default` mode) will ask once more for write tools; this is accepted (choice D).
- **Limits.** Input and result at most 1 MiB each (a longer result is cut and says so);
  4 calls in flight per session (more wait); a call ends after the tool plugin's call
  limit of guest time and 5 minutes of wall time; cancelling the turn cancels its calls;
  64 tools listed per plugin.

## Git and GitHub

**`kumikit.git`** (kind `tool`, `integration`):
- Tools (all `read`): `status`, `diff` (path, staged), `log` (count, path), `show` (rev,
  path), `branches`. No write tools in M5: agents already commit with their own shell,
  and write approvals are proved by GitHub's `create_pull_request` and the test tool
  plugin.
- Methods (scope `workspace`) for the panel: `status`, `diff`, `log`.
- Permissions: `spawn = ["git"]`; no network, no secrets, `files = "none"`.
- It runs `git -c core.fsmonitor=false -c core.hooksPath=<empty> --no-pager` with
  `--no-ext-diff --no-textconv` where they apply and `GIT_TERMINAL_PROMPT=0`,
  `GIT_OPTIONAL_LOCKS=0`, so a repository's configuration cannot start fsmonitor, hooks,
  external diff or textconv programs. Clean/smudge filters can still run (git runs them
  on `status`); install says `git` runs with your full access, as for every `spawn`.
- Output is parsed from porcelain formats (`status --porcelain=v2 -z`, `log -z
  --format=…`), pure functions tested natively; the end-to-end test runs real `git` in a
  temp repository (git is on every CI runner).

**`kumikit.ui-git`** (level 2 panel, `inspector.tab` "Changes"): changed files with their
status, a diff for the selected file (rendered with theme tokens, no HTML from git), and
the last 20 commits. `requires.core = ["kumikit.git@^0.1"]`, `network = []`. It refreshes
when the panel is shown, on a refresh button, and when the tab's workspace topic reports a
turn ending (`thread.updated`), never on a timer.

**`kumikit.github`** (kind `tool`):
- Tools: `pull_request_get`, `pull_requests_list`, `issue_get`, `issues_list`,
  `checks_for_ref` (all `read`), `create_pull_request`, `create_issue_comment` (`write`).
  Inputs carry `owner` and `repo`, as GitHub's own MCP server does, so the plugin needs no
  file access to read the remote.
- Permissions: `network = ["api.github.com"]`, `secrets = ["github-token"]`. No spawn, no
  files. The settings page has one `x-secret` field for the token (a fine-grained token is
  recommended in its description).
- Rate limits: it reads `X-RateLimit-Remaining` and `Retry-After` and returns a tool error
  saying when to retry; it never retries in a loop.
- No panel in M5 (the tools are for agents; a PR panel can come later).
- Tests: request building and response parsing are pure and tested natively; end to end
  against `test-plugins/fake-github` (canned responses, records requests so a test can
  check the `Authorization` header and bodies) through `KUMIKIT_TEST_HTTP_ROUTES`.

## Telegram bot

`kumikit.bot-telegram`, world `kumikit:bot/plugin@0.1.0`:

```toml
[activation]
on = ["startup"]
[permissions]
network = ["api.telegram.org"]
secrets = ["telegram-bot-token"]
client = ["workspaces.list", "threads.read", "threads.create", "threads.send", "threads.cancel", "approvals.respond"]
workspaces = "linked"
[[contributes.commands]]
id = "pair"
title = "Telegram: pair a chat"
```

- **Running.** `bot.run` starts on its own instance when the plugin is enabled and the
  token is set; it long-polls `getUpdates` (timeout 50 s) and waits on that request and on
  its kernel subscriptions at once (`wasi:io/poll`). It returns when stopped; a failure
  restarts it with the host's backoff. With the bot enabled, the core contacts
  `api.telegram.org` continuously: the README privacy section and the install text say so.
- **Pairing a chat** (mirrors device pairing, [02](../spec/02-protocol.md#pairing)): the
  `pair` command shows a one-time code (8 characters of Crockford base32, 5 minutes, one
  use, burnt after 5 wrong tries, one live code; stored in `kv` as a hash). The user sends
  `/pair ABCD-EFGH` to the bot from a **private** chat; the bot records the chat id and
  the Telegram user id. Paired chats are listed on the bot's settings page with "Unpair".
  Group chats are refused in M5 (anyone in the group could talk to the agent).
- **Approvals from Telegram are on by default** for paired chats, as Allow and Deny only.
- **What a paired chat can do:** `/workspaces`, `/new <workspace> [provider]`, `/threads`,
  `/use <n>`, plain text (sent to the current thread), `/cancel`. The bot relays
  `text.done` (not deltas), approval requests (with Allow / Deny buttons; no "always"),
  and the turn's end. Approvals answered there are recorded with `plugin`.
- **Workspaces** must be linked to the bot by the user (plugin page, A6); the bot sees no
  other.
- **Rate limits.** Outgoing: at most 1 message per second per chat and 25 per second in
  total, coalescing text that piles up; on `429` it waits `retry_after`. Incoming: at most
  10 messages per minute per chat start or queue turns; more get one "slow down" reply.
  Unpaired chats get one "not paired" reply per chat per hour, then silence.
- **Secrets.** The token is set from the settings page (`x-secret`), read with
  `secrets.get` only when `run` starts; it is in the request path, which the host never
  logs (A5).
- **Code shape.** Update parsing, the command state machine, pairing and the rate limiter
  are pure Rust, tested natively; `exit_m5.rs::telegram` drives the built component
  against `test-plugins/fake-telegram` (Bot API subset: `getUpdates` with long polling,
  `sendMessage`, `editMessageText`, `answerCallbackQuery`; a control channel injects
  updates and reads what was sent).
- **Spec 09** changes: the world is `kumikit:bot@0.1.0` (not `@1.0.0`), the client
  interface moves to `kumikit:host/client` (schedules use it too), the permission words
  are A6's, `workspaces = "linked"` replaces `"chosen"`.

## Schedules

- **Activation model.** A schedule belongs to a plugin: either a manifest trigger
  `schedule:<cron>` (owned by the manifest) or one the plugin sets with
  `timers.set(key, { cron, time-zone, description, missed })`. When one is due the kernel
  activates the plugin (control instance) and calls `timers.fire(key, due)`; the plugin
  does the work (the schedules plugin starts a thread through the client interface).
- **Cron:** five fields (minute, hour, day of month, month, day of week), lists, ranges,
  steps, and `@hourly`/`@daily`/`@weekly`/`@monthly`; no seconds field, so the shortest
  interval is one minute. Own parser in the kernel with test vectors (no cron crate). Time
  zone: the core's local zone by default, or an IANA name, through `jiff`; DST gaps run at
  the next valid minute, repeated hours run once.
- **Persistence.** Rows in the core database (migration); `next_run` is stored so a
  restart needs no replay.
- **Idle.** One scheduler task. It sleeps until the earliest enabled `next_run`, or waits
  only for a change notification when there is none. No polling, no wakeups at idle
  without schedules (kernel test counts armed timers; footprint phase unchanged).
- **Missed runs.** At start, and after a wake more than 5 minutes late (sleep, suspend):
  policy `skip` (default) records `missed` and moves on; `once` runs once now. Never more
  than one catch-up per schedule.
- **Overlap.** A schedule does not fire while its previous `fire` call is still running;
  the run is recorded as `skipped`.
- **Limits.** 64 schedules per plugin; `fire` gets the usual call limits.
- **Seeing and stopping.** `schedule.list` shows every schedule on the core with its
  plugin, description, cron, zone, next run and last outcome; `schedule.setEnabled` pauses
  or resumes one; `schedule.delete` removes a timer (manifest triggers can only be
  paused). `ui-settings` gets a "Schedules" page. Disabling the plugin stops all its
  schedules; uninstalling deletes them. A thread started by a schedule shows `from {
  plugin }`.
- **`kumikit.schedules`** (kind `integration`): scheduled prompts. Command "New scheduled
  prompt" returns a declarative form (workspace, provider, prompt, cron, new thread each

## ADR 0020's freeze review

## Security: new surfaces against 11-security

| Threat | Control | Proved by |
|---|---|---|
| Another local process or user reaches the gateway's tools | MCP only through the local socket (0600, peer check; pipe ACL); a per-session 256-bit token in memory, passed in the environment, void when the session ends | gateway tests: no token, wrong token, ended session, remote `gateway.attach` |
| A provider hands tool access to its agent without consent | A session gets a gateway only if its plugin was granted `tools`, shown at install | test: provider without `tools` gets none |
| A tool acts outside the calling thread's workspace | The tool instance acts for that thread's workspace; `process.spawn` checks cwd | test |
| A tool changes things without the user knowing | `write` tools need an approval in the turn; every call is a `tool.*` event with `source` | test |
| A plugin sends data to a host it did not declare, or reaches the LAN | `network` allowlist on every request, https only, no automatic redirects, resolved addresses must be public unless the entry is a private literal | A5 tests |
| A secret in a URL reaches a log (Telegram) | The host logs only the host of a request; known secret values are redacted from logs | log scan tests (A1, E3, E4) |
| A bot or schedule acts beyond its grant | `client` operations and `workspaces` enforced by the kernel; no `allow_always` from plugins; actions recorded with `plugin` | A6 tests |
| A stranger messages the bot | Pairing code shown only in Kumikit (40 bits, 5 minutes, one use, burnt after 5 tries); private chats only; chat and user id both checked | bot unit tests and E4 |
| A stolen Telegram account drives the agent | Only linked workspaces; approvals only `allow`/`deny`; rate limits; "Unpair" and disabling the plugin stop it at once | E4 |
| Conversation text leaves the machine through a bot | Install shows the host; README privacy section; nothing is sent before a chat is paired | review |
| Something runs on a schedule unnoticed | `schedules` permission shown at install; `schedule.list` and the Schedules page; pause and delete; threads say `from` | E5 |
| A git repository's config runs programs | fsmonitor, hooks, external diff and textconv disabled; filters still run, as for any git command; `spawn` says git runs with your access | git tests |

Rows added to 11-security in the steps that build them.

## Footprint

Budgets unchanged in the spec. Baseline: core binary 30.5 MiB of 32 (M4), idle 11.9 / 12.9 /
15.4 MB, UI kernel 66.9 KB, installers ≤ 17.1 MB.

**The core binary may pass its budget during M5 (decided 2026-11-19).** No step stops for
it. Each step that adds code records the binary size in Notes; if it passes 32 MiB, the
footprint script reports the binary instead of failing on it, with a line in this plan and
in the roadmap's M5 status saying so, and optimisation (an own HTTP interface, fat LTO,
`opt-level = "s"` for wasmtime and Cranelift, trimming features) is a separate task after
M5. Expected growth: `wasmtime-wasi-http` and its bindings (perhaps 0.5–1 MiB), `jiff` (a
few hundred KiB), the gateway, scheduler, settings and client interface (about 0.3 MiB).

Other measures (gated as today): idle with every M5 plugin enabled and none active
(nothing new resident; a new footprint phase); idle with the Telegram bot running (one
resident instance, reported against the activation budget of 16 MB); no armed timer with
no schedules (test); the gateway opens no listener (startup check, like M4's "no registry
file"). UI kernel: core commands and results and the schedules page, about +5 KB gzip.
