# M7 — Threads: queue, steering, handoff and deferred messages

- **Goal:** Make the chat panel a full working surface for agent threads: a durable,
  editable message queue; steering a running agent; switching agent mid-thread with a
  context handoff; messages that wait for a time, another thread or a command (a build, CI);
  forks, edit-and-resend and side threads; and the composer and transcript tools users
  expect ([roadmap](../spec/12-roadmap.md#m7--threads), [02-protocol](../spec/02-protocol.md),
  [03-kernel](../spec/03-kernel.md), [05-providers](../spec/05-providers.md),
  [07-ui-plugins](../spec/07-ui-plugins.md)).
- **Status:** active (steps 0 and 1 done; step 2 in progress on `feat/m7-steering`).

## Why now

Users of coding-agent workspaces now expect most of what is below. Kumikit can offer it
without per-agent special cases, because the kernel owns the domain model
([ADR 0006](../decisions/0006-kernel-owns-domain-model.md)): the queue, steering and
handoffs become general thread features that every provider and client gets.

WIT (`kumikit:host@0.2.0`, `kumikit:provider@0.2.0`) and the UI SDK (`0.1.x`) are still
0.x ([ADR 0020](../decisions/0020-interface-freeze-after-m5.md)). M7 needs new provider
and host versions (steering, handoff context, attachments as a real field). They should
land in M7, before the 1.0 freeze.

## What Kumikit has today and what is missing

| Area | Kumikit now | Wanted | Gap |
|---|---|---|---|
| Messages sent during a turn | In-memory FIFO in `turns.rs`; dropped on cancel, lost on restart; the client shows them as plain "Queued" bubbles | Stored in SQLite; edit, reorder, remove, **Send now**, **Steer**; held (not dropped) after a stop, a failure, a restart or a usage limit, with **Resume** | Durable, editable, visible queue with hold rules |
| Steer a running agent | None (`send` blocks for the whole turn) | Native on Claude Code (stream input), Codex, OpenCode and others; ⌘/Ctrl+Enter; falls back to the queue, shows "Not steered" | Steering API for providers, kernel inbox, fallback |
| Switch agent mid-thread | `thread.update` changes `model` and `permissionMode` only; `provider` is fixed | Switch provider while idle; the next message carries bounded history (200 messages, 64 KiB, truncation disclosed); "Conversation carried forward" row; old replies keep their author label | Provider change with a handoff, per-turn attribution |
| Wait for a build, CI, another thread | Only plugin-owned cron schedules (`kumikit.schedules`) | Per-thread wake-ups: in N minutes, at a time, every N minutes, weekly, **after another thread finishes**; agents create them with tools; a fired wake-up queues if the agent is busy | Deferred messages with triggers, including "after a command exits", and agent tools for them |
| Fork / edit a sent prompt | None | Fork from a message; **Edit** forks to just before a prompt and puts its text back in the composer | `thread.fork` with a cut point |
| Side questions | None | `/btw`: a side thread that can read the main thread, in an inspector tab, never steers the main run | Side threads linked to a parent |
| Composer | Text, attachments, model and permission pickers, branch pill | `/` commands discovered from each provider, `@` file mentions, per-thread drafts | Slash commands from providers, mentions, drafts, prompt history |
| Transcript | Messages, tool calls, reasoning, file changes, approvals | One card per turn with running step and elapsed time; grouped tool calls; changed-files summary with diffs; Copy/Fork/Edit actions; find in thread; approval bar with **Approve all** | Turn cards, per-turn change summary, message actions, find, approval bar |
| Limits and checks | Turn ends `failed` | "Limited" status with reset time; queue held and resumed at reset; optional post-turn check command that queues one fix message | Limit events, resume at reset, turn checks |

Out of scope for M7 (later milestones or never): agent teams and model routing, account
pools, cloud agents, Codex goals, design canvas and visual progress, scenes and
wallpapers, a task board. Bots stay where the roadmap puts them.

## Design summary

These are the shapes the ADRs (step 0) must confirm. Names follow the protocol rules:
camelCase fields, snake_case enum values, additions are minor changes.

### 1. Durable queue

- A table `queued_messages { id, thread, position, input (JSON: text, attachments),
  trigger (JSON, nullable), created, updated, from? }`. A message sent during a turn becomes
  a row, not a `VecDeque` entry.
- The queue is thread content, so changes are thread events: `queue.added { entry }`,
  `queue.updated { entry }`, `queue.removed { entry, reason }` (`sent`, `steered`,
  `removed`, `cancelled`), `queue.moved { order }`, `queue.held { reason }`
  (`stopped`, `failed`, `restarted`, `limited`), `queue.resumed`. `thread.get` returns
  `queue` and `queueHold?` in its snapshot.
- Methods: `thread.queue.update { entry, input }`, `thread.queue.remove { entry }`,
  `thread.queue.move { entry, before? }`, `thread.queue.sendNow { entry }` (idle: start it;
  running: steer if possible, otherwise cancel the turn and send it next),
  `thread.queue.resume`.
- Behavior change: `thread.cancel` **holds** the queue instead of dropping it (users lose
  typed work today). A failed turn and a core restart hold it too. Changing the published
  "drops queued messages" rule needs an ADR and a protocol minor bump with the old
  behavior described as superseded.
- `thread.send` keeps its result shape (`turn`, `queued`) and adds `entry` when queued.

### 2. Steering

- `kumikit:turn@0.1.0` adds `interface input { take: func() -> result<option<user-input>,
  error>; read-stdout: func(child: borrow<child>, max: u32) -> result<read, error>; }`
  alongside `kumikit:host@0.2.0` and `kumikit:provider@0.2.0`, plus `world provider`
  (listed next to `kumikit:provider/plugin@0.2.0` in a steering provider's manifest) and
  `interface client { steer: ... }`. `read-stdout` races stdout and the turn's input inbox
  inside the host (preferring waiting input over stdout). This fits session instances and
  WASI 0.2 blocking `send` ([ADR 0010](../decisions/0010-wasi-p2-and-session-instances.md));
  no re-entrant call into a busy instance, and 0.2 providers keep working unchanged.
- Models report a new capability `steer`. `provider-claude` writes a stream-json user
  message to stdin; `provider-acp` reports `steer` only for agents whose manifest entry
  sets `steer = true` (none by default) and sends a second `session/prompt`.
- `thread.steer { thread, input }` → `{ status, turn, entry? }`: `accepted` (in the inbox),
  `queued` (no `steer` capability, attachments, or the turn ended first: the input becomes
  the queue's first entry with `reason: "not_steered"`), `conflict` when no turn runs (use
  `thread.send`). The kernel emits `input.steered { turn, input }` when the provider takes
  the input, so the transcript shows it where the agent saw it. Inputs still in the inbox
  when the turn ends move to the head of the queue with `queue.added { front: true,
  reason: "not_steered" }`.
- Attachments are not steerable in M7: the client offers Steer only for text.
- Client interface: a `threads.steer` operation (`kumikit:turn/client@0.1.0`), so tools
  and bots can steer.

### 3. Provider switch and handoff

- `thread.update` accepts `provider` (with `model`) while the thread is idle. The kernel
  ends the session, clears the stored `resume` id (a native id never crosses providers),
  and appends `thread.switched { from { provider, model }, to { provider, model },
  handoff }`, where `handoff` is `transcript` (default) or `summary`.
- `turn.started` gains `provider` and `model`, so every turn keeps its author after later
  switches (the UI labels replies by turn, not by the thread's current provider).
- Handoff context: `kumikit:provider@0.3.0` adds `user-input.context:
  option<handoff-context>` with `from-provider`, `from-model`, `messages` (JSON array of
  `{ role, text, turn }`, user and assistant text only: no tool calls, reasoning or
  attachment bytes), `files-changed` (paths from `file.changed`), `truncated`, `summary?`.
  Bounds: newest 200 messages and 64 KiB encoded; truncation is stated. `sdk/rust` gets a
  helper that renders the context as a prompt preamble, so providers format it the same
  way. For a 0.2 provider the kernel prepends that rendered text to `user-input.text`.
- The handoff is pending until a turn on the new provider ends `done` and the provider has
  returned a session id; then `handoff.delivered` is appended. A cancelled or failed first
  turn keeps it pending, so the next message carries it again.
- `summary` mode: before switching, the kernel runs one turn on the outgoing provider with
  a fixed prompt ("Write a handoff note for another agent: goal, decisions, state, open
  items, files"), marked `turn.started { purpose: "handoff_summary" }`; its `text.done`
  becomes `context.summary`, and the bounded transcript is still attached.
- The same mechanism serves forks (below) and threads whose session id was lost.
- Composer: the provider picker stays enabled in an existing idle thread; picking another
  provider shows a small "Hand off to X" confirmation with the two modes. The transcript
  shows a "Conversation carried forward from Claude Code" divider that expands to the
  exact context sent.

### 4. Deferred messages (wake-ups)

A deferred message is a queue entry with a `trigger`. It shows in the same queue UI with
its condition, and when its trigger fires it joins the queue like any message (so a busy
agent gets it after its turn, never in the middle).

- Triggers: `at { time }`, `after_turn { thread, onlyOnSuccess? }` (another thread, or this
  one, finishes its running turn), `after_command { argv, cwd?, timeoutS }` (the kernel
  runs the command under its process supervisor; on exit the message is sent with the
  exit code and the last 8 KiB of output appended), and `poll_command { argv, everyS,
  maxTries }` (run until it exits 0: "when CI is green", "when the build passes").
  Recurring cron schedules stay in `kumikit.schedules`.
- The fired message carries a short trailer that tells the agent why it woke
  (`Deferred message: after "cargo build --release" exited 0 · set by this thread's agent`),
  and `turn.started.from` names the source (`user`, a plugin, or `{ deferred: entry }`).
- Durability: rows survive restarts. `at` triggers that passed while the core was down
  fire once at startup. `after_command` processes do not survive a restart; their entries
  are held with `queue.held { reason: "restarted" }` and offer Re-run.
- Loops: an `after_turn` chain that leads back to its own thread is refused with
  `invalid_params` ("would loop"). An agent-created trigger needs `maxRuns`-style limits:
  at most 10 pending agent deferred messages per thread.
- Commands: a client may set any `after_command`/`poll_command` (the user is the actor).
  A plugin needs `spawn` covering the program, and its call goes through an approval of
  kind `command` unless the thread's permission mode is `full_access`.
- Composer: the send button gets a menu (**Send later…**: in N minutes, at a time, after
  thread…, when a command succeeds) and `/later` as a client command.

### 5. Agent tools for threads

A first-party core plugin, `kumikit.threads` (in its own repository like the others,
[ADR 0026](../decisions/0026-first-party-plugins-in-their-own-repositories.md)), uses
only the client interface and contributes gateway tools:
`wake_me` (deferred message to the calling thread), `message_thread`, `list_threads`,
`read_thread` (bounded, paged), `list_queue`, `queue_message`, `steer_thread`,
`suggest_title`. The calling thread comes from `tool-call.thread`. `message_thread` and
`steer_thread` to another thread are `write` tools (approval); `wake_me`, `list_*`,
`read_thread` and `suggest_title` are `read`. The kernel gains the client operations it
needs (`threads.steer`, `threads.queue`, `threads.defer`, `threads.title.suggest`);
none of them names a plugin.

`suggest_title` sets the title only while it was never renamed by a user (`Thread.titleSource`:
`auto`, `agent`, `user`).

### 6. Forks, edit-and-resend, side threads

- `thread.fork { thread, atTurn?, beforeTurn?, title? }` → `thread`. Copies the thread's
  events up to the cut into a new thread (same workspace, worktree, provider, model, mode;
  new ids, `forkedFrom { thread, turn }`), with no `resume` id, so the first turn carries a
  handoff context. Capability `fork` lets a provider fork natively later; M7 uses the
  handoff for all.
- Edit a sent prompt: fork `beforeTurn` and put that turn's text (and attachments) back in
  the new thread's composer. The source thread is unchanged. Files are not rewound; the UI
  says so.
- Side threads: `thread.create { parent, side: true }` makes a thread linked to a parent,
  hidden from the sidebar's main list. Each message to it carries a bounded "main thread
  context" (the parent's messages it has not seen, capped at 24 KiB). `/btw <question>`
  opens or reuses it in an inspector tab (a `thread.view` mounted in `inspector.tab`), with
  **Insert into main** on answers. It never queues into or steers the parent.

### 7. Composer and transcript

- **Slash commands.** Provider event `commands.available { commands: [{ name,
  description?, hint? }] }` (thread event; `provider-acp` maps `available_commands_update`,
  `provider-claude` maps its `system/init` command list). The composer lists them with
  client commands (`/model`, `/later`, `/btw`, `/fork`, `/rename`), filters as you type,
  and never runs one on selection.
- **@ mentions.** `@` searches `workspace.files.list` (worktree-aware), inserts a quoted
  path; nothing is read or attached.
- **Drafts and history.** Per-thread drafts kept in client settings; Up in an empty
  composer recalls the thread's last prompts.
- **Turn cards.** Each turn shows its provider/model, running step and elapsed time;
  consecutive tool calls collapse into groups of five with counts and failures; the
  final reply stays open.
- **Changes per turn.** A footer lists the files a turn changed (from `file.changed`) with
  added/removed counts and opens their diffs.
- **Message actions.** Copy, Fork from here, Edit (user messages), copy-code on fenced
  blocks, jump to bottom.
- **Find in thread.** Ctrl/⌘+F inside a thread pane highlights matches in loaded
  messages.
- **Approval bar.** Pending approvals sit in one line each above the composer, with
  **Approve all** when there are several (each still a separate `respondApproval`).

### 8. Limits and turn checks

- Provider event `limit.reached { resetAt?, message }`: the thread status becomes
  `limited`, the queue is held with `limited`, and the kernel arms an `at` resume for
  `resetAt` (unknown reset: manual Resume only). Status dots and the composer banner show
  it.
- Turn checks (opt-in per workspace in client settings, off by default): after a turn ends
  `done` with file changes, the client queues a deferred `after_command` for the
  workspace's check command with "fix this" as an editable message, sent only on failure.
  This reuses step 4; no new kernel feature.

## Exit

1. Messages typed during a turn are listed above the composer, can be edited, reordered,
   removed and sent now; after Stop, a failed turn or a core restart they are held in
   order until Resume.
2. With Claude Code (recorded transcript), Ctrl/⌘+Enter during a turn steers the agent:
   the input appears in the transcript where the agent took it, and the turn continues.
   With a provider without `steer`, the same action queues the message.
3. A thread started on Claude Code switches to an ACP agent while idle; the ACP agent's
   first prompt holds the bounded earlier conversation; earlier replies keep their Claude
   Code label; a cancelled first turn resends the handoff.
4. An agent calls `wake_me` with "when `<build command>` succeeds"; the core runs the
   command, and when it exits 0 the thread gets the wake-up message with the output tail,
   queued if the agent is busy. A wake-up set for 5 minutes fires once after a core
   restart.
5. Edit on an earlier prompt opens a fork without that prompt and with its text in the
   composer; `/btw` answers a side question while the main turn keeps running.
6. All existing checks (axe in both themes, UI rules, bundle budget, unit, browser and
   desktop exit tests) pass.

## Notes

- Kumikit's deferred messages live in the core, not the window, so they keep running with
  the window closed and on remote cores.
- Steering cannot be a second call into the session instance: `send` holds the instance for
  the whole turn. The inbox plus pollable keeps the one-call-at-a-time rule.
- Decided in the ADRs: deferred messages get their own method, `thread.defer`
  (a distinct result and client operation); queue changes are thread events, so replay
  stays exact; the `summary` handoff turn is shown collapsed and labelled, and falls back
  to `transcript` mode if it fails.
- `thread.send` during a held queue resumes it (ADR 0027), so older clients are not stuck
  after Stop.
- Step 1: when a turn ends, the run is dropped before `turn.ended` is appended (under the
  dispatch lock), so a client reacting to `turn.ended` with `thread.update` finds the
  thread idle. Appending `turn.ended` after the decision was a regression caught by
  `thread_update_changes_mode_and_restarts_idle_session`.
- Step 1: `sendNow` while a turn runs holds the rest of the queue (the run was stopped);
  `sendNow` on an idle thread leaves an existing hold in place.
